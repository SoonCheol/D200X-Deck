# DeckForge Store Server 0.1.6 (development)
Independent single-container service. No changes to the editor or existing NAS. Python/Flask/Gunicorn, SQLite, immutable content-addressed blobs. Initial deployment is intentionally not automatic.

## Test
`python -m pip install -r requirements.txt`, then `python -m unittest discover -s tests -v` from store/. Tests use a temporary directory and Flask test client.

## Build / Portainer preparation
From store/ build `docker build -t deckforge-store:0.1.6 .` on a trusted builder. The Compose template expects a verified image reference, explicit HTTPS origin and unused proxy port. The NAS reverse proxy must reach the internal port; if it is in a separate container, configure a private shared network instead of exposing the service publicly. Do not deploy the sample blindly. Review and pin the base image digest and transitive dependency hashes before production. No default password, no signup. Initialize the owner interactively using `docker exec -it deckforge-store python server.py create-owner OWNER_NAME`. Password minimum 12 characters. Owner can add and disable users. Back up the database and immutable blobs together with the service stopped; restore to a separate volume and test before production. Never expose /data as webroot. HTTPS must be enforced by the reverse proxy. Configure request body size <=61 MiB and timeouts/rate limits. No external NAS credentials or paths are embedded.

## Publishing and signing
Upload parses archive bounds, validates raster images, collects sample previews and classification tags, and stores an immutable draft. Direct SVG archive imports remain rejected; folder creation accepts a restricted static SVG subset and indexes PNG only. Package structural inspection is not malware detection or full independent SDK validation. Administrator reviews provenance/license and explicitly publishes. Third-party content is always private. Only current published release is served, and all list/detail/download/HEAD requests require authentication. Withdraw retains original blobs and metadata. Old releases can be reselected by explicit publish. Versions are immutable; same item/version conflicts. Browser cookie is Secure/HttpOnly/SameSite Strict, mutations check Origin + custom header; desktop bearer session is hashed at rest and expires in one hour.

For independently reviewed native packages, generate/store an Ed25519 private key outside the service and use local CLI `python server.py sign-release RELEASE_ID PRIVATE_KEY_PEM` with the same database and STORE_ORIGIN while service is stopped or on an approved admin environment. No HTTP signing/private key endpoint. Public key is distributed independently and manually pinned in DeckForge. Signing is a deliberate admin attestation; never sign unreviewed code. Key rotation requires publishing with the new key and explicit re-pin; operational ceremony not tested. Actual server/client integration, resource stress, dependency lock/hashes, security audit, Docker build and restore drill remain pending.

## Offline review and signing (0.1.1)
Owner can inspect draft previews, correct independent purpose/naming/design classifications, and download the original for review. Published own native releases expose a signing-request JSON in the admin detail. Download the original, review with the editor's independent validator and inspect the source/permissions; keep the Ed25519 private key off the NAS. On a trusted signing machine with this version's dependencies, run `python signing.py REQUEST_JSON PACKAGE PRIVATE_KEY_PEM SIGNATURE_JSON`. Verify the origin and package identity before signing. Import SIGNATURE_JSON through the admin detail; the server validates the signature against the current metadata before storing it. Independently distribute the public key and its fingerprint for desktop pinning. Signing does not constitute malware analysis; server never executes uploaded code. The legacy local CLI signing command is still available but offline signing is preferred. Previous releases are preserved; only current published release is served.

## Deployment candidate archive (0.1.6)
The push workflow builds an amd64 image after API/restore/signature/loopback TLS tests and Compose smoke testing, and stores an image tar.gz with SHA256SUMS, Compose and source revision in the GitHub Actions artifact. It does not publish to GHCR or deploy. Before importing, check `sha256sum -c SHA256SUMS` in the extracted artifact directory and `docker load -i deckforge-store-0.1.6.tar.gz` on an explicitly approved host. Set DECKFORGE_STORE_IMAGE=deckforge-store:0.1.6 in the Stack, choose the actual origin/port and proxy network only after inspecting the NAS. Artifact retention 3 days to limit storage; rebuild from the same source if expired. The archive checksum detects corruption, not independent publisher authenticity. Production dependency hash/digest pinning, web GUI/desktop installation and real NAS reverse-proxy validation remain separate. Local tests generate ephemeral self-signed TLS certificates and pass the CA only to the child test process; no OS trust modifications.

## Folder icon pack creation
Owner can select a folder in a browser supporting directory selection, edit pack name/version/author, search and preview raster files, edit individual tags or add/remove tags on selected rows. Relative paths and image bytes are preserved in a ZIP with manifest.json and icons.json; other non-image files are explicitly counted and excluded. Limits: 2500 images, 58 MiB source total, 6 MiB per image, 1 MiB index, 30 tags per icon. SVG folder files are limited to 256 KiB each, 500 SVGs, 2530 archive entries including originals, and a 60 second conversion budget. Original SVG bytes are preserved under originals/; the index uses PNG paths. A same-name PNG conflict rejects the upload. Unsupported SVG features (scripts, references, CSS, gradients, filters, text rendering, animation) are rejected, not silently stripped. Owner can explicitly request a PNG preview before registration. The Linux child is resource-limited, not a separate network/filesystem sandbox; production hardening and dependency pinning remain pending. The AI helper only prepares a selected-name prompt and imports user-pasted JSON suggestions after confirmation; no AI service is called, no automatic translation, no API key or cost. Pack creation stays in draft, with existing review/publication rules. Existing file upload unchanged.

0.1.4 adds large multipart upload regression tests and actual editor icon pack parser cross-check, including Korean user-supplied tags. Multipart non-file field buffer remains bounded at 128 KiB; JSON API body retains its 16 KiB cap. No desktop source change.

## Catalog search (0.1.6)
The existing authenticated catalog endpoint accepts optional q (120 characters, literal Unicode-normalized substring), purpose, naming and design filters. All apply before cursor pagination and after the authorization predicates. Metadata fields include name, author, version, description, package ID and classification tags. Newly uploaded icon packs also have private server-side filename/name/tag search records, not sent in API metadata. Existing releases retain metadata search; their individual icon search records are not backfilled in this version. The web catalog uses server-side search, with a short debounce and reset pagination on changed filters. Existing desktop clients can continue to call the unfiltered endpoint; desktop search UI wiring is separate.
